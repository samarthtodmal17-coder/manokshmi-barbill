## Loophole audit — fixed in code
1. **PIN brute force**: 4-digit PINs had no limit. Now 5 wrong tries lock login 60 s (doubling, max 15 min), persisted across restarts; flagged entry in the activity log.
2. **Staff could delete paid bills** from History (soft delete, but cash could be pocketed). Delete is now Owner-only when logins are in use; a blocked attempt is flagged in the log. (Staff can still EDIT bills — every edit is logged with who/what; I left that because fixing a wrong item right after billing is a legitimate job. Ask me if I want it restricted.)
3. **System clock tampering** (changing the PC date to back-date bills): app now records the last-seen time and flags "System clock moved backwards" in the activity log if the clock jumps back >10 min. Cannot be prevented client-side, only detected.
4. **Data safety**: browser storage → SQLite on disk + daily external backups; unlicensed copy never reads data.
5. **Offline**: Excel/QR libraries bundled; no CDN dependency.
6. Already in the original app and kept: selling below zero stock is allowed but flagged in the activity log; deleted bills are kept (marked deleted) and excluded from reports; edits keep an edit log.

## Known limits / things I must be told honestly
- Staff PINs and the recovery code are stored in plain text inside the data and therefore inside the backup JSON files in Documents. Anyone with Windows access to the PC can read them. PINs are a counter-misuse gate, not a security boundary (same stance as RestroBill). Hardening would mean hashing PINs — not done.
- With no staff accounts created, everyone is effectively Owner (the app shows a banner). Consider requiring owner setup at first run.
- Every save rewrites the whole collection (e.g. all bills) as JSON; very large histories (years of bills) will save slower. The app's Archive feature in Setup > Data & Performance mitigates this.
- Excise register/return formats and the SCM upload must be checked against CURRENT Maharashtra rules by an excise consultant or a pilot bar owner before I promise compliance. Nothing about legal compliance was verified.
- Tested here (sandbox): adapter tests (queue, retry, coalescing, atomic multi-key, failure recovery, 5 MB value), and jsdom simulations: licence gate before data read, activation, data load into SQLite, backup file, export interception, external links, print shim, safe close, PIN lockout, staff delete blocked. NOT tested: Rust compile (the first GitHub Actions run is the real compile check), real Windows printing (bill/KOT/barcode labels), real WebView2 behaviour, the installer, auto-update.
